# fetch-rig

Universal HTTP client built exclusively on `fetch()` and `AbortController` — runs identically in browsers, Node.js 20+, Deno, Bun, and Cloudflare Workers.

## Install

```bash
npm install fetch-rig
```

## Core Exports

| Export | Purpose |
|---|---|
| `fr` | Default `FetchInstance` — use directly or as the base for `fr.create(config)` |
| `FetchInstance` | The class `fr` is an instance of |
| `FetchResponse` | Wraps `Response` — parse body, stream |
| `retry` | Built-in retry — always added explicitly to `middlewares`, there is no config shortcut |
| `FetchError` / `HTTPError` / `NetworkError` / `TimeoutError` / `CanceledError` | Error hierarchy |

## Instance Setup

```typescript
import { fr } from "fetch-rig";

// Use the default instance directly — no config needed
await fr.get("https://api.example.com/ping");

// Or create a scoped instance
const api = fr.create({
  baseUrl: "https://api.example.com",
  headers: { Authorization: "Bearer token" },
  timeout: 5_000,             // ms, single timeout
  throwOnError: false,        // default — non-2xx returns normally, doesn't throw
  middlewares: [authMiddleware, retry({ limit: 2 })],
});
```

`fr` is **not** a special namespace object — it's a `FetchInstance` created with empty config. `fr.get(...)` just calls the default instance; `fr.create(config)` returns a new, independently-configured instance. There's no global mutable state to worry about between instances.

## REST Methods

```typescript
await api.get(url, options?)     // Promise<FetchResponse>
await api.head(url, options?)
await api.options(url, options?)
await api.delete(url, options?)
await api.post(url, body?, options?)
await api.put(url, body?, options?)
await api.patch(url, body?, options?)
await api.send({ method, url, body, ...options })  // low-level, when you need a dynamic method
```

Every method resolves to `Promise<FetchResponse>` — it does **not** throw on a non-2xx status unless `throwOnError: true` is set (instance-level default or per-call override). Check `response.ok` / `response.status` directly, or opt into throwing (see [Errors](#errors)).

## `FetchResponse` — body parsing

```typescript
res.ok          // boolean, true for 2xx
res.status      // number
res.statusText  // string
res.headers     // Headers
res.url         // string
res.redirected  // boolean
res.type        // ResponseType — 'basic' | 'cors' | 'default' | 'error' | 'opaque' | 'opaqueredirect'
res.bodyUsed    // boolean — true once any body-reading method (or stream()) has been called

const data  = await res.json<MyType>();  // generic goes on json<T>(), not on get<T>()
const text  = await res.text();
const blob  = await res.blob();
const buf   = await res.arrayBuffer();
const bytes = await res.bytes();
const form  = await res.formData();
```

**Body reads are single-use, same as native `Response`.** If you need both parsed data and headers/status, read `res.status` etc. first (cheap, synchronous getters), then call exactly one body-reading method. If you need to read the body more than once (e.g. `.text()` for logging and `.json()` for parsing), call `res.clone()` first — same one-clone-before-first-read rule as native `Response.clone()` — and read from the clone and the original separately.

## Automatic Request Body Serialization

```typescript
await api.post("/users", { name: "Ada" });          // → JSON, Content-Type auto-set
await api.post("/upload", formData);                 // → FormData passed through, boundary set by runtime
await api.post("/upload", blob);                     // → Blob passed through, Content-Type from blob.type
await api.post("/legacy", params, {
  headers: { "Content-Type": "application/x-www-form-urlencoded" },
});                                                    // → object is urlencoded instead of JSON, because of the header
```

Detection uses **both** the body's type and any Content-Type you've already set — not type alone. Full table in [references/api.md](references/api.md#automatic-body-serialization). Key gotcha: **never manually set a `multipart/form-data` Content-Type header yourself** when passing `FormData` — the boundary is generated by the runtime, and fetch-rig will strip a stale one for you, but setting your own will break the upload.

## Cancellation & Timeout

Standard `AbortController` — there is no custom cancel-token class:

```typescript
const controller = new AbortController();
setTimeout(() => controller.abort(), 2000);
try {
  await api.get("/slow", { signal: controller.signal });
} catch (error) {
  if (error instanceof CanceledError) { /* controller.abort() was called */ }
}
```

`timeout` (ms) is available at both instance and per-call level and produces `TimeoutError` (distinct from `CanceledError`, which is for explicit `signal.abort()`).

## Middleware — auth refresh, logging, custom retry placement

`next` is a plain, repeatable function — not a Koa-style single-use callback — which is what makes "call the rest of the chain again after refreshing a token" straightforward:

```typescript
import type { FetchMiddleware } from "fetch-rig";

const authMiddleware: FetchMiddleware = (next) => async (ctx) => {
  ctx.request.headers.set("Authorization", `Bearer ${getToken()}`);
  await next(ctx);

  if (ctx.response?.status === 401) {
    await refreshToken();
    ctx.request = ctx.request.clone(); // already sent once — MUST clone before reusing
    ctx.request.headers.set("Authorization", `Bearer ${getToken()}`);
    await next(ctx);
  }
};

const api = fr.create({ baseUrl: "...", middlewares: [authMiddleware] });
```

Middlewares registered in an array run outer-to-inner on the way in and inner-to-outer on the way out (onion order) — the first middleware in the array wraps everything else. Full contract and `FetchContext` shape: [references/middleware-retry.md](references/middleware-retry.md).

## Retry

There is **no `retry` config field** — the built-in retry is the `retry` middleware, added to `middlewares` like any other:

```typescript
import { retry } from "fetch-rig";

const api = fr.create({
  middlewares: [
    retry({
      limit: 2,                                    // default
      statusCodes: [408, 429, 500, 502, 503, 504], // default
      minTimeout: 300, factor: 2,                   // exponential backoff, default
      jitter: true,                                  // off by default
    }),
  ],
});
```

Where you place it in the array matters: earlier (more outward) means more of the stack re-runs on each retry attempt.

Retries only idempotent methods by default (GET/HEAD/OPTIONS/PUT/DELETE/TRACE/QUERY — **not POST**, since blindly retrying a non-idempotent request risks duplicating a side effect if the server already processed it). A `CanceledError` (explicit user cancellation) is never retried by default either. Full options and `Retry-After` handling: [references/middleware-retry.md](references/middleware-retry.md).

## Upload / Download Progress

```typescript
await api.post("/upload", file, {
  onUpload: (event) => console.log(`${(event.progress * 100).toFixed(0)}% at ${event.rate ?? 0} B/s`),
});

const res = await api.get("/large-file", {
  onDownload: (event) => console.log(`${event.loaded} bytes, ~${event.estimated ?? "?"}s left`),
});
```

The callback parameter is conventionally named `event`, not `progress` — the field `event.progress` would otherwise stutter against a parameter also named `progress`.

`rate` (bytes/sec) and `estimated` (seconds remaining) are a simple running average since the first chunk — not a smoothed/recent-window estimate — and both are `undefined` until there's been measurable elapsed time (`estimated` additionally needs `total` to be known).

**Important gotcha**: on some runtimes (verified: Chrome without HTTP/2, and Firefox), `onUpload` never fires at all even though the upload succeeds normally — this is expected, documented behavior, not a bug to work around. Never assume `onUpload` fired at least once as a way to confirm an upload happened; check the resolved response instead. Full explanation: [references/progress.md](references/progress.md).

### Capping response size

```typescript
const api = fr.create({ baseUrl: "...", maxDownloadBytes: 10 * 1024 * 1024 }); // instance default, overridable per call
```

Aborts the response (throwing `TooLargeError`) once real received bytes exceed the limit — not the `Content-Length` header, which can lie or be missing. **Gotcha**: `await api.get(url, { maxDownloadBytes })` itself still resolves normally even if the body will end up too large — `fetch()` resolves once headers arrive, before the body is read, so the error only surfaces when you call `.text()`/`.json()`/etc. on the response. Full details: [references/progress.md](references/progress.md).

## Streaming Responses (SSE / JSON Lines / text)

```typescript
const res = await api.get("/stream");

for await (const item of res.stream()) { }        // format: 'auto' — Content-Type detected
for await (const event of res.streamAsSse()) {     // event.event, event.data, event.id, event.retry
  if (event.event === "done") break;               // breaking early still cancels the underlying connection
}
for await (const chunk of res.streamAsJson()) { }  // chunk.data is a raw JSON string — JSON.parse it yourself; chunk.error is set instead if it failed to parse
for await (const line of res.streamAsText()) { }   // line.data, one line per item
```

**`streamAsJson()` is NDJSON-only** — a single top-level JSON array response (`[{...},{...}]`) arrives as *one* value once the whole array is received, not streamed element-by-element. If an endpoint might return either NDJSON or a single big array, don't assume per-element streaming. A line that fails to parse is yielded with `.error` set (not thrown, not silently dropped) — check `chunk.error` before parsing `chunk.data`. Full type shapes and the LLM-token-streaming pattern: [references/streaming.md](references/streaming.md).

## Errors

```typescript
import { HTTPError, NetworkError, TimeoutError, CanceledError, TooLargeError } from "fetch-rig";

try {
  await api.get("/might-fail", { throwOnError: true });
} catch (error) {
  if (error instanceof HTTPError) {
    console.error(error.response.status, error.data); // data is pre-parsed from a clone
  } else if (error instanceof TimeoutError) {
    console.error("timed out");
  } else if (error instanceof CanceledError) {
    console.error("cancelled:", error.reason);
  } else if (error instanceof TooLargeError) {
    console.error(`too large: ${error.transferredBytes}/${error.maxDownloadBytes} bytes`);
  } else if (error instanceof NetworkError) {
    console.error("network failure:", error.cause); // DNS/connection failure, not a cancellation
  }
}
```

`throwOnError` defaults to `false` — without it, check `response.ok`/`response.status` instead of wrapping every call in try/catch. `HTTPError.data` is pre-read from a clone, so `error.response.json()`/`.text()` still work afterward too.

`throwOnError` also accepts `(status: number) => boolean` to fully replace the default non-2xx check with your own (e.g. treat 3xx as success too). **If you know axios's `validateStatus`, note the polarity is inverted**: axios's function returns `true` for "this is fine, don't throw"; fetch-rig's returns `true` for "throw for this status" — matching what `throwOnError: true` already means as a boolean. The function is not additionally gated by `response.ok`, so it can also throw for a 2xx status if you return `true` for one.

**Do not check `error.name === "AbortError"`** (the habit from raw `fetch()`/`AbortController`) — use `error instanceof CanceledError` instead. fetch-rig's `timeout` option also aborts a signal internally, so a bare `"AbortError"` name check can't tell a real cancellation apart from a timeout; `instanceof CanceledError` vs `instanceof TimeoutError` can. The original reason (a native `AbortError` `DOMException` if `controller.abort()` was called with no argument) is preserved unchanged at `error.reason`.
